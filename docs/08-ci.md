# Continuous Integration

## Workflow 分離

Frontend 與 backend 使用獨立 GitHub Actions workflow，各自使用 path
filter。

好處：

-   frontend change 不需要啟動 PostgreSQL。
-   backend change 不需要安裝 frontend dependencies。
-   failure surface 比單一大型 workflow 清楚。
-   workflow file 本身也納入 path filter，修改 CI 時一定會驗證 CI。

## Frontend pipeline

``` text
npm ci
→ lint:ci
→ type-check
→ test:unit:ci
→ build-only
```

### lint

CI 不執行 auto-fix。Local developer command 可以提供 fix，但 CI
的責任是驗證 source tree 本身是否符合規則。

Oxlint 與 ESLint 都執行，即使其中一個先失敗也不讓另一個被 `&&`
短路；最終只要任一失敗，step 仍失敗。

Warnings 視為 failure，避免 warning 變成永久背景噪音。

### type-check 與 build 分開

不使用把 type-check / build 平行包在一起的 convenience script。CI UI
應直接顯示是哪一個 concern 失敗，log 也不互相交錯。

## Backend pipeline

``` text
PostgreSQL healthy
→ install dependencies
→ ruff check
→ alembic upgrade head
→ alembic check
→ pytest
```

## 為什麼 CI 使用兩個 database

Backend CI 的 migration 與 pytest 使用不同 database：

``` text
easyfigma_ci       → Alembic
easyfigma_ci_test  → pytest
```

原因是 test harness 使用 ORM metadata `create_all()` 建 schema，而
migration test 使用 Alembic 建 schema 並維護 `alembic_version`。

兩者若共用 database，測試的是兩套互相干擾的 schema bootstrap，而不是
application behavior。

### 取捨

可以強迫 pytest 也只用 migration 建 DB，但那會把每個 test session 的
application test setup 綁死 migration lifecycle。v1 保留兩個 concern：

-   Alembic pipeline 驗 migration correctness / drift。
-   pytest database 驗 application behavior。

## Environment mapping

CI 專用 URL 使用 CI 名稱保存，再只在需要的 step 映射成 application
期待的 `DATABASE_URL` / `TEST_DATABASE_URL`。

測試用 secret 是 runner configuration placeholder，不與 production
secret 共用。

## 原則

CI 不只是「跑測試」；它把 repository 的可重建性變成 executable
contract：

-   clean install 是否成功。
-   migration 是否能從空 DB 到 head。
-   ORM metadata 是否 drift。
-   static analysis 是否通過。
-   tests 是否通過。
-   frontend 是否能完成 production build。
